## 분석 결과

### 현재 프로필 사진 업로드 방식

**업로드 흐름:**
1. `AvatarUpload` 컴포넌트에서 `useBase64={true}` 설정
2. 파일 선택 → FileReader로 Base64 인코딩
3. `handleAvatarChange(base64Image)` 콜백으로 상위 컴포넌트에 전달
4. "프로필 저장" 클릭 시 `/api/user/profile` PUT 요청
5. **users 테이블의 `avatar_image` 컬럼에 Base64 문자열로 직접 저장**

```
사용자 → AvatarUpload (Base64 변환) → profileData.avatar_image 
→ /user/profile API → users.avatar_image 컬럼
```

### Users 테이블 구조

| 컬럼 | 타입 | 용도 |
|------|------|------|
| `avatar_image` | TEXT | Base64 인코딩된 이미지 (현재 사용) |
| `avatar_url` | VARCHAR | 외부 URL (레거시, 미사용) |

## 결론 및 권장사항

### 현재 방식 (Base64 직접 저장) 유지를 권장

**이유:**
1. **간단한 구현**: 별도 파일 관리 로직 불필요
2. **데이터 일관성**: 사용자 삭제 시 이미지도 함께 삭제
3. **백업 용이**: DB 백업만으로 모든 데이터 보존
4. **이미 구현 완료**: 현재 정상 작동 중

**단점 (허용 가능):**
- DB 용량 약간 증가 (Base64는 ~33% 오버헤드)
- 프로필 이미지는 보통 100KB~1MB로 작아서 큰 문제 없음

### `PROFILE_IMAGE` attachment_type 활용 시나리오

1. **향후 파일 시스템 저장으로 전환할 때**: attachments 테이블 + 파일 시스템 조합
2. **프로필 이미지 히스토리 관리**: 사용자가 변경한 이미지 기록 보관
3. **대용량 이미지 지원 필요 시**: DB 부하 감소 목적

### 최종 결론

```
현재 상태: users.avatar_image에 Base64로 저장 ✅ (적절함)

PROFILE_IMAGE attachment_type: 현재 미사용으로 두고, 
향후 파일 시스템 기반으로 전환할 때 활용
```

프로필 사진은 사용자당 1개만 필요하고, 용량도 작으므로 현재 방식이 합리적입니다.

## 방안 1: DB 설계 (권장)

```
conversations (대화 세션)
├── messages (개별 메시지)
├── code_changes (코드 변경사항)
├── files_touched (수정된 파일)
└── conversation_tags (태그)
```

### 스키마 설계

```sql
-- 대화 세션
CREATE TABLE conversations (
    id VARCHAR(50) PRIMARY KEY,
    title VARCHAR(500),              -- 대화 제목/요약
    project_path VARCHAR(1000),      -- 프로젝트 경로
    branch_name VARCHAR(200),        -- Git 브랜치
    summary TEXT,                    -- AI가 생성한 요약
    learning_points TEXT,            -- 핵심 학습 포인트
    difficulty_level VARCHAR(20),    -- easy/medium/hard
    category VARCHAR(100),           -- bug-fix, feature, refactor 등
    status VARCHAR(20) DEFAULT 'active',
    started_at TIMESTAMP WITH TIME ZONE,
    ended_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 메시지
CREATE TABLE conversation_messages (
    id VARCHAR(50) PRIMARY KEY,
    conversation_id VARCHAR(50) REFERENCES conversations(id),
    role VARCHAR(20) NOT NULL,       -- 'user' or 'assistant'
    content TEXT NOT NULL,
    token_count INTEGER,
    "order" INTEGER,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 코드 변경사항
CREATE TABLE conversation_code_changes (
    id VARCHAR(50) PRIMARY KEY,
    conversation_id VARCHAR(50) REFERENCES conversations(id),
    message_id VARCHAR(50) REFERENCES conversation_messages(id),
    file_path VARCHAR(1000),
    change_type VARCHAR(20),         -- create/edit/delete
    language VARCHAR(50),
    code_before TEXT,
    code_after TEXT,
    explanation TEXT,                -- 변경 이유 설명
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 태그
CREATE TABLE conversation_tags (
    id VARCHAR(50) PRIMARY KEY,
    name VARCHAR(100) UNIQUE,
    color VARCHAR(20),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- 대화-태그 연결
CREATE TABLE conversation_tag_mappings (
    conversation_id VARCHAR(50) REFERENCES conversations(id),
    tag_id VARCHAR(50) REFERENCES conversation_tags(id),
    PRIMARY KEY (conversation_id, tag_id)
);

-- 전문 검색 인덱스
CREATE INDEX idx_messages_content_search ON conversation_messages 
    USING gin(to_tsvector('english', content));
```

```json
"scripts": {
  "migrate:conversations": "node scripts/migrate-conversations.js --db-only"
}
```

이렇게 하면 `npm run migrate:conversations`로 실행할 수 있습니다.
